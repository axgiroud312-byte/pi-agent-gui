# #34: Native Agent service to Pi RPC contract

Status: implementation in progress. Acceptance remains the latest text and comments of GitHub Issue #34. The 2026-09-23 user clarification prioritizes the native GUI experience, not compatibility with the old Agent internals; #34 is the current stopping point, later tickets remain pending confirmation.

## Ownership and execution

- The existing ZCode workbench, Lexical composer, pane state, native components, layout, streaming/tool cards, scroll, tabs, split panes and observable feedback remain the user interface. The desktop host owns workspace identity, task association, window layout and the connection to the renderer. The v4 conversation transport is a current low-cost presentation seam, **not** a requirement to preserve the old Agent's internal service architecture.
- One **active Pi RPC process per session** owns Agent execution, tools, the Pi JSONL history, the steering and follow-up queues, retry and compaction. The host never runs a second model loop. A session is addressed by its Pi session file and Pi session ID; neither is a ZCode task ID, command ID, row ID or process generation. A native task-list row projected from that session is display data, not permission to run a ZCode task.
- Pi is the only authority for messages, tools, history, run state and queues. The product must select a Pi service implementation at every executable Agent boundary. Each Agent action either reaches Pi or fails visibly as unsupported; compatibility no-ops must not claim unsupported capabilities succeeded. The original ZCode CLI is reserved for separately marked reference runs; no product fallback may launch it. The desktop Host supplies the Pi entry to `createLocalServices`; unsupported legacy task commands fail closed at its Pi Agent service proxy. The remote desktop connector is explicitly unavailable in #34 **before** it can launch its old `zcode-server`, pending a Pi-backed execution target. The standalone HTTP/stdio server still defaults to the ZCode Agent and is not a Pi desktop product entry; it must be migrated or isolated before being offered as a product server.
- Pi CLI authentication, session history and resources use the user's selected Pi profile on the execution target. `ZCODE_DESKTOP_PROFILE_HOME` continues to isolate application metadata and must not silently relocate Pi's own data or change execution `HOME`/`USERPROFILE`. The app-owned bookmark stores only Pi JSONL pointers; `.pi-agent-ide.lock` serializes **product Host** writers and recovers a dead PID. A separate Pi CLI does not honor this advisory lock: simultaneous external CLI writes are not yet proven safe.

## Commands and state

| Native observation | Pi authority and mapping |
| --- | --- |
| `createSession` | Spawn a new pinned Pi 0.87.0 RPC process in the workspace, query `get_state`, record Pi session ID/file and bind a native session. An empty draft may appear transiently in the Pi sessions index but is **not** a durable task/history entry without Pi JSONL. |
| `sendText` / first input | Send one Pi `prompt` with a correlated native command ID. Its successful response means accepted only. Mark the run complete only after Pi `agent_settled`, or after a verified no-run extension command state. |
| `stop` | Fence the current execution generation, resolve or cancel pending extension interactions, send Pi `clear_queue` then `abort`, and verify the resulting Pi state. Late events from the old generation cannot revive the run. |
| Native v4 subscription | Return an ACK with a unique subscription ID, then publish a schema-valid initial snapshot frame. Subsequent Pi events publish monotone deltas or full snapshots. Each frame carries its own epoch, cursor and delivery kind. A resync with a mismatched base sends a full snapshot. |
| Sessions index | Project only Pi-backed sessions, including current phase and last activity. A workspace's session list is not inferred from renderer tabs. |
| History | Read Pi JSONL through Pi's public RPC/session APIs; restored messages and tool output must match the completed live projection. Reconnect queries current state and never resends an input with uncertain delivery. |

For streaming, apply Pi `message_update.assistantMessageEvent` by `contentIndex`; `message_end.message` replaces the provisional content. `tool_execution_update.partialResult` is cumulative and replaces the prior partial result. Pi `read` input keeps its original JSON in `inputText`; its native clickable file chip resolves relative paths against the Pi session workspace, not the Electron/Host cwd. Native completed-turn work history is collapsed by default: expand the original history trigger to see the Pi tool card; clicking its README chip must open the **same workspace file** Pi read. `agent_end` is only a low-level cycle boundary. `agent_settled` is the completed run boundary. Retry, compaction and extension commands may change this sequence. Unknown Pi records remain observable in diagnostics rather than being invented as successful UI state.

The v4 command ACK reports admission, and the v4 snapshot/delta reports execution. A process exit settles outstanding requests for that session only. A timed-out or interrupted write can have unknown delivery; the host must query the actual Pi session before any retry and must never replay a possibly executed side effect automatically.

## Transport and version

- Pinned executable: `@earendil-works/pi-coding-agent@0.87.0`, release commit `16787ad5b2dc748047f314ca1bfe7708f30f54f3`, MIT. The installed package's `dist/bundle/cli.js` is invoked with `--mode rpc` through a Node-compatible process, without a shell shim.
- RPC is Pi's stdin/stdout JSONL protocol, not ZCode's request/notification protocol. LF frames, optional CRLF, split UTF-8, `U+2028`/`U+2029`, stderr isolation, request ID and command correlation, single-writer backpressure, byte limits and child exit are transport obligations.
- `packages/services/src/pi-agent/pi-rpc-client.ts` and `rpc-jsonl.ts` are copied from this repository's locally authored historical prototype at `46c34f18011030024225cf71fd3e829dc31a57b4`; the related process fixture and tests are migrated with them. No upstream Pi source was copied. The historical tests are evidence for the transport only and must run again in the native tree.

## #34 evidence gate

The issue stays open until the built native GUI creates a Pi session, streams real Pi text and a real tool, stops it, and restores Pi history; two simultaneous Pi processes are shown isolated. Focused protocol tests, native service/renderer contract tests, actual package entry, GUI screenshots and a fixed-version Pi process test are required. The current locally built Windows installer/unpacked executable passes the five-operation GUI probe plus 1280×800/1920×1080 light/dark checks; see `pi-34-packaged-final/` in the isolated evidence root. This uses a deterministic **model provider**, while the read tool runs inside a real pinned Pi subprocess; no online-provider inference is claimed. This is not a pixel-by-pixel upstream comparison or an installer upgrade test. Independent Standards and Spec review must cover the complete PR merge base, then current Windows CI and merge close the ticket.
